# 站点图标：服务端抓取 + KV 缓存 + 手动上传覆盖

## 为什么覆盖规范

规范 R-5.2 原本规定「站点标识是『色块 + 首字』，不是 favicon」，并明确禁止外链第三方图标服务。用户明确要求真图标，因此本条规范被覆盖。**但「色块 + 首字」保留为兜底**：抓不到图标、或用户没手动传时，仍然显示识别色方块 + 白色首字，任何情况下都不出现裂图或灰色占位框。

## 为什么不用第三方图标服务

本机（中国大陆网络）实测：

| 服务 | 结果 |
|---|---|
| `www.google.com/s2/favicons` | 不通 |
| `icons.duckduckgo.com` | 不通 |
| `favicon.im` | 不通 |
| `icon.horse` | 通，但属境外第三方，规范也禁止 |

所以改由边缘函数抓取、缓存进 KV、从自己域名发出，浏览器只与本服务通信。

## 抓取策略

1. 先抓站点首页 HTML，解析 `<link rel="...icon...">`（`apple-touch-icon` 的 rel 同样含 icon，会一并命中）。
2. 以上都失败再退到 `<origin>/favicon.ico`。
3. **每个候选都必须校验 `content-type` 是 `image/*` 或 `x-icon`** —— 实测 `cloud.tencent.com/favicon.ico` 返回的是 `200 + text/html`（SPA 首页），只判断状态码会把整页 HTML 当成图标存下来。
4. 单个图标上限 200 KB，超过则跳过。

这一步是必要的：种子数据里 `少数派` 的 `/favicon.ico` 是 404，只有解析 HTML 才能拿到它的图标。

## 手动上传覆盖

- `POST /api/icon?id=<linkId>`（body = 图片字节，需口令）→ KV 记 `{ manual:1, ct, b64 }`
- `GET /api/icon?id=<linkId>` → **手动的一律优先，且不随链接 URL 变化而失效**
- `DELETE /api/icon?id=<linkId>` → 抹掉，改回自动抓取

## 安全与代价

- 图标接口**只接受 linkId，绝不接受客户端传 URL**，URL 一律从 KV 的链接列表里查出来，所以它不是开放代理，不存在 SSRF。
- **认证方式后来改了（见下方修订）**：原方案是 `GET` 不校验口令，理由是「`<img>` 标签带不了自定义请求头」，
  并认为「图标本来就是各站点的公开图片」所以可接受。
- 写入类操作（`POST`/`DELETE`）要求口令。
- **已知代价**：新建链接时先传图标再落盘（否则新增的链接在 KV 里还不存在），所以如果传完图标又取消新建，会留下一个几 KB 的孤儿图标。数量有界，可接受。

## 修订：图标接口改为 Cookie 认证（要求「书签不能公开」之后）

原先的推理有一个漏洞：**图标本身是公开的，但「你收藏了哪些站点」不是。**
`/api/icon?id=<linkId>` 公开意味着：任何知道某个 linkId 的人都能确认「这个 linkId 对应的站点存在」，
从而推断出书签清单的内容。虽然 linkId 带随机后缀、不易枚举，但这仍然是一次信息泄露，不能留。

修法：认证从「只认请求头」扩展为「请求头 **或** HttpOnly Cookie」。

- `/api/data` 校验口令成功后，响应里种下 `nav_auth=<口令的 SHA-256>`（HttpOnly / Secure / SameSite=Lax）。
  Cookie 里存的是**哈希不是明文口令**，避免把口令本身留在浏览器里。
- `/api/icon` 的 `GET`/`POST`/`DELETE` 都要求通过认证；`<img>` 发起的 GET 会自动带上 Cookie。
- `Secure` 只在 HTTPS 下附加——本地 dev 是 `http://127.0.0.1`，带 `Secure` 浏览器会直接丢弃 Cookie。

顺序上必须保证「先拿到数据、再渲染图标」：`app.js` 是先 `GET /api/data`（此时种下 Cookie）再 `render()`，
所以图标请求一定带着凭据。这一点改动渲染顺序时容易踩坏。
